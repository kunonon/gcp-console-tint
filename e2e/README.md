# End-to-end tests

The WebdriverIO suite installs the built Chrome MV3 and Firefox MV2 extensions in separate browser profiles and drives them in Chrome and Firefox. The default Compose run builds both artifacts and runs the suite serially under Xvfb:

```sh
docker compose --profile e2e run --rm --build e2e
```

CI runs four end-to-end jobs, each on its own runner: Chrome and Firefox, each split into `ui.e2e.mjs` and the remaining spec files. Each CI container mounts the host pnpm store, restored from the Actions cache; local Compose behavior is unchanged. The default local command above remains serial. For parallel local runs, run these commands in separate terminals with different `--project-name` values, which isolate their `node_modules`, `.wxt`, and `.output` volumes:

```sh
docker compose --project-name e2e-chrome --profile e2e run --rm --build -e E2E_BROWSER=chrome e2e
docker compose --project-name e2e-firefox --profile e2e run --rm --build -e E2E_BROWSER=firefox e2e
```

To run one browser, add `-e E2E_BROWSER=chrome` or `-e E2E_BROWSER=firefox` before `e2e`. To run some spec files only, add `-e E2E_SPECS="e2e/smoke.e2e.mjs"` (space-separated paths); without it, every `e2e/*.e2e.mjs` file runs. If pnpm is available on the host, the optional launchers are `pnpm test:e2e`, `pnpm test:e2e:chrome`, and `pnpm test:e2e:firefox`; the Compose command requires no host pnpm installation. Failed harness runs retain screenshots, page captures, and startup diagnostics under `.e2e-artifacts/`. Successful runs remove their own run directory, leaving earlier failures untouched. When the container runs as root, artifact ownership is restored to the mounted checkout's UID/GID so Linux users can inspect and remove their diagnostics.

## Browser versions and downloads

Local runs follow Chrome and Firefox `stable` at runtime by default. This catches compatibility changes in current browsers, but the same commit can fail after a browser or driver release. CI pins the browser and Geckodriver versions shown below; update those pins together with a successful both-browser run. These downloads are outside `pnpm-lock.yaml` and `minimumReleaseAge`. WebdriverIO does not supply an expected archive hash to the downloader; npm lockfile integrity does not verify these browser archives.

To use the CI browser and driver versions locally, pass the pinned overrides to Compose explicitly:

```sh
docker compose --profile e2e run --rm --build \
  -e E2E_CHROME_VERSION=157.0.8103.38 \
  -e E2E_FIREFOX_VERSION=stable_159.0.1 \
  -e GECKODRIVER_VERSION=0.37.1 e2e
```

ChromeDriver follows the resolved Chrome version. Firefox stable versions need the `stable_` prefix; a bare numeric Firefox build ID is interpreted as Nightly by the downloader. Geckodriver selects its own latest release unless `GECKODRIVER_VERSION` is supplied. The Docker base image and apt packages can still change, so these overrides do not freeze the entire container environment. Extension discovery uses Chrome's internal developer API and Firefox's internal UUID preference, which can change across browser versions.

The service currently targets `linux/amd64`. Apple Silicon hosts run it through x86 emulation, which can make local runs slower; native Linux arm64 execution of this suite has not been verified.

WebdriverIO 10 downloads browsers through `@puppeteer/browsers` 3, which does not depend on `extract-zip`. (WebdriverIO 9 required the 2.x line, which did, so a pnpm override replaced it until the upgrade.) `extract-zip` has two high-severity advisories with no patched release (GHSA-jmr9-qjv8-65gv, GHSA-7pqw-9j4j-h8q3), so CI checks that it stays out of the dependency graph, and a dependency update that brings it back fails the build. `pnpm why extract-zip` shows which package brings it in.

WebdriverIO 10 makes `$` strict: a selector that matches more than one element throws `StrictSelectorError` instead of returning the first match. Narrow the selector, or use `$$` when several matches are expected.

This service assumes direct network access for browser downloads. Host `HTTP_PROXY` / `HTTPS_PROXY` variables are not forwarded by default, and the selected Puppeteer downloader has no installed `proxy-agent` peer. Proxy-based browser and driver downloads are not supported or verified by this setup. The browser's local fixture proxy is configured separately and is unrelated to download proxy support.

## Execution and validation

Both browsers run with visible windows on Xvfb; Firefox pointer input depends on that display. The service sets `TZ=Asia/Tokyo`, and the export check fixes a time at which the local and UTC calendar dates differ. Reduced motion is requested explicitly by its separate suite so normal cases keep their transition checks.

The Node runner uses `--test-force-exit` because standalone WebdriverIO can leave browser/driver handles active. In particular, if session creation rejects after a driver starts, no browser object is returned to the harness for `deleteSession()`. `init: true` and the one-shot Compose container bound those processes to the container lifetime; forced exit is not proof that JavaScript cleanup completed. Assertions and awaited harness cleanup still determine the test result.

The `.mjs` harness and specs receive Biome lint and real browser execution; they are outside the application TypeScript check. The default Compose command always rebuilds both artifacts. `test:e2e:run` is an internal command: running it directly can reuse older build output whose manifest version still matches the checkout.

## Scope and limits

The browser tests use a local HTTPS fixture served as `console.cloud.google.com` and `outside.example.test`. It has the small set of elements and SPA controls required by the tests; the proxy rejects other network targets. These tests do not exercise Google sign-in, live Console pages, Google's production DOM, or its real navigation implementation.

The settings screen is opened at the extension's `sidepanel.html` URL in a WebDriver tab. The smoke test separately verifies native opening: Firefox clicks the toolbar action and checks the browser sidebar's open state; Chrome checks `openPanelOnActionClick`, makes a trusted click on a button in the extension page to call `sidePanel.open`, and confirms a real `SIDE_PANEL` runtime context. It does not click Chrome's operating-system toolbar icon. Import uses WebDriver to provide a path to the actual file input, and export reads the downloaded file from the isolated test directory; native OS file-picker, permission, and download-prompt windows are outside the test boundary.

Drags are WebDriver pointer actions, the same actions in both browsers: the rule list reorders on pointer events from its grips, not on HTML drag-and-drop, so no OS-level input is needed. The reorder tests drag a grip a few steps past the middle of the target row, never onto a midpoint; one checks that a drag starting on the rule text changes nothing, and the selection test drags rows 1 and 3 of four by the first one's grip past the last row and expects them together at the end. Hovering is a WebDriver pointer move onto the row, without a press, so the checkboxes are revealed by a real `:hover`; the always-shown checkboxes of `(hover: none)` devices are not exercised. The tests do not synthesize DOM events. The colour editor is the extension's own popover, so it is driven like a user would: clicks, typed keys, and pointer actions for drags on the colour well (react-aria listens to pointer events too) and on a gradient's stops. No browser or OS colour dialog is involved. The drags assert the direction of the change (hue kept or left, which thumb moved) and that the thumb followed the pointer to where the drag ended, not an exact colour per pixel, and the secondary mouse button, touch input, and arrow keys on the thumbs are not exercised here.

Coverage is by the scenarios in the table, not every cross-product of match mode, color, platform, and browser setting. The content suite exercises all eight combinations of the three surface enable flags, but other combinations are representative examples. The run targets Chrome and Firefox in the Linux container; it does not cover every browser release, operating system, profile, or display configuration.

Stored settings are read strictly, as an import is: a value that cannot be read whole is refused, never repaired with defaults. The extension-reload cases check that unversioned, unsupported older, non-settings, partly invalid, and newer stored values stay as they are and paint nothing after visible startup and a bounded observation period, with the side panel on its recovery screen, and that a current schema is kept as it is. They do not prove that storage writes never occurred; unit tests use a storage spy for that contract. They also seed v0.1.3 storage with a 2.5px top bar height and check that it paints 3px before the reload and is stored with height 3 under the current stamp after it, and they seed 0.2.0 storage written before the theme existed and check that the 0.3.0 migration step adds theme `auto` while keeping the rule, and that the 0.5.0 step wraps the seed's plain bar colors as `{ type: "solid", color }` while the text color stays a string. Negative origin checks and unrelated-key stability also have finite observation windows, rather than proving that no later change is possible. Stripe E2E checks cover the stripe overlay's application/removal and fixed alignment; unit tests cover the exact angle, width, and light/dark phase. Parser coverage includes six of the seven `SettingsImportError` refusal reasons (`migration-failed` is unit-tested only, since no migration step throws on a JSON object except with its own invalid-fields refusal); filesystem permission failures and inaccessible-file dialogs are not simulated.

The theme the side panel opens in is checked by its mechanism, not by its frames. `ui.e2e.mjs` checks that the built page loads `theme-init.js` as a classic script in `<head>` ahead of the React bundle, that the built script turns the `localStorage` hint (or, without one, the system scheme) into the `dark` class, and that the hint follows the stored theme, a stale hint being corrected after a reload. Whether a wrong-coloured first frame is painted is not observable here: WebDriver Classic, which the Firefox run uses, cannot install a recorder ahead of the page's own scripts.
